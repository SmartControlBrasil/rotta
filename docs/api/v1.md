# Rotta 116 API v1

Current versioned application API under:

```text
/api/v1/
```

The v1 interface currently serves the Flutter driver application and customer freight-request flows. Business rules remain in the application/domain layers; views translate HTTP input/output and enforce the appropriate authentication adapter.

## Authentication

### Login

`POST /api/v1/auth/token/`

Request:

```json
{
  "username": "driver_or_email",
  "password": "secret"
}
```

Success:

```json
{
  "access_token": "signed-access-token",
  "refresh_token": "signed-refresh-token",
  "expires_in": 900
}
```

### Refresh

`POST /api/v1/auth/token/refresh/`

```json
{
  "refresh_token": "signed-refresh-token"
}
```

Returns a new access token. Invalid/expired refresh tokens return `401`.

### Revoke

`POST /api/v1/auth/token/revoke/`

Requires mobile authentication. Revokes the current access token and can also revoke a supplied refresh token.

## Driver Identity And Capabilities

### Me

`GET /api/v1/me/`

Returns authenticated user, linked driver, organization and permission-derived capabilities.

The current `DRIVER` role is intentionally limited to operation/tracking capabilities. Endpoint-level ownership still restricts the driver to assigned operations.

## Driver Preferences

### Read/update preferences

```text
GET /api/v1/driver/preferences/
PUT /api/v1/driver/preferences/
```

Preferences represent persistent geographic/operational settings used by matching evolution.

### Route intents

```text
GET  /api/v1/driver/route-intents/
POST /api/v1/driver/route-intents/
POST /api/v1/driver/route-intents/<uuid>/cancel/
```

Route intents capture time-bounded desired routes/directions and optional vehicle/cargo preferences. Vehicle references must belong to the driver's organization and satisfy assignment rules enforced by the service.

## Driver Operations

### List assigned operations

`GET /api/v1/driver/operations/`

Supports page/page_size pagination (page size capped by the implementation).

Representative result fields:

```json
{
  "count": 1,
  "next": null,
  "previous": null,
  "results": [
    {
      "id": "operation-uuid",
      "status": "ASSIGNED",
      "reference_code": "...",
      "assigned_at": "2026-08-22T12:00:00-03:00",
      "origin": "Campinas",
      "destination": "Santos",
      "load_type": "LTL",
      "service_level_state": null
    }
  ]
}
```

Only operations assigned to the authenticated driver are returned.

### Operation detail

`GET /api/v1/driver/operations/<operation_uuid>/`

The response includes, when available:

- operation status/reference.
- carrier, driver and vehicle.
- origin/destination projection.
- **operational stops** with `id`, `sequence`, `stop_type`, `status` and `has_pod` when snapshot stops exist.
- cargo profile/weight/volume/temperature limits.
- tracking-session state.
- POD summary.
- load type, ETA/delay and SLA summary.
- operational timeline.
- thermal summary/excursion information.

Operational stops are authoritative for running multi-stop journeys. Legacy fallback to request stops exists only for operations without operational stop snapshots.

### Advance operation status

`POST /api/v1/driver/operations/<operation_uuid>/advance-status/`

The body requests the next status. The backend state machine decides whether the transition is legal.

Current high-level flow:

```text
ASSIGNED
→ DRIVER_EN_ROUTE_TO_PICKUP
→ ARRIVED_AT_PICKUP
→ LOADING
→ IN_TRANSIT
→ ARRIVED_AT_DELIVERY
→ UNLOADING
→ DELIVERED
```

Do not treat this endpoint as arbitrary status assignment.

### Advance operational stop

`POST /api/v1/driver/operations/<operation_uuid>/stops/<stop_uuid>/advance-status/`

Used for ordered multi-stop execution. Application rules enforce:

- stop belongs to the assigned operation.
- legal stop-state transition.
- previous-stop sequence integrity.
- cargo pickup-before-delivery integrity.
- POD requirement before completing delivery stops where applicable.
- idempotent retry behavior.

### Report incident

`POST /api/v1/driver/operations/<operation_uuid>/incidents/`

Creates an operational incident event. Reporting an incident does **not** replace the FreightOperation main status.

### Record POD

`POST /api/v1/driver/operations/<operation_uuid>/pod/`

For multi-stop operations, the body can identify a delivery stop (`stop_id`) so the POD belongs to that delivery.

Important semantics:

- operation/stop ownership is validated.
- multi-stop POD is accepted for the appropriate delivery-stop state.
- legacy operation-level POD remains supported for compatible simple operations.
- equivalent retries return the existing POD.
- materially conflicting repeat payloads return a business conflict.

A multi-stop FreightOperation can have multiple PODs. New integrations must not assume one POD per operation.

## GPS Tracking

### Start tracking

`POST /api/v1/driver/operations/<operation_uuid>/tracking/start/`

Creates or returns the active TrackingSession for the assigned operation. Concurrent starts are serialized so duplicate active sessions are avoided.

### Record location

`POST /api/v1/tracking/<session_uuid>/locations/`

Records a GPS point for the authenticated driver's active session.

The contract supports telemetry fields such as coordinates, accuracy and optional retry identifiers/sequence according to the current view/service implementation.

Latitude/longitude and other numeric data are validated by the application service.

### Record offline/batch locations

`POST /api/v1/tracking/<session_uuid>/locations/batch/`

Used for queued/offline mobile telemetry synchronization.

Retry safety is based on explicit identifiers (`client_event_id`) and/or sequence. Device timestamp alone is not a uniqueness key.

### End tracking

`POST /api/v1/tracking/<session_uuid>/end/`

Ends the authenticated driver's tracking session. Terminal operation flows also close active tracking sessions when applicable.

## Thermal Telemetry

### Record thermal reading

`POST /api/v1/driver/operations/<operation_uuid>/thermal-readings/`

Thermal telemetry is separate from GPS.

The service supports sensor/device identity, sensor timestamp, temperature, quality/validity, idempotency metadata and thermal-excursion evaluation against configured cargo limits.

The response indicates whether the reading was created or deduplicated and may include current active-excursion information.

## Customer Freight Requests

Customer endpoints use the customer authentication adapter rather than driver ownership.

### List/create

```text
GET  /api/v1/customer/freight-requests/
POST /api/v1/customer/freight-requests/
```

POST creates a freight request through the customer application service. Current payloads include origin, destination and cargo data; service validation remains authoritative.

### Detail

`GET /api/v1/customer/freight-requests/<request_uuid>/`

The query is customer-scoped so one customer cannot retrieve another customer's request by UUID.

## Error And Security Rules

See `conventions.md` for the common error, idempotency, multi-tenancy and concurrency rules.

Driver-resource endpoints intentionally return not-found semantics for inaccessible resources when appropriate to avoid leaking cross-driver/cross-tenant existence.

## Compatibility Notes

- `FreightOperation` is currently structurally tied to marketplace Selection origin. This will be generalized before contracted recurring routes are implemented.
- `operation.pods` is the canonical multi-POD relation. Any legacy single-POD compatibility behavior must not be used as a new API assumption.
- Flutter is a client adapter. Never copy state-machine/RBAC logic into mobile code as a second source of truth.
